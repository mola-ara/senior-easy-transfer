# 바다송금 제품 기획서 (Product Brief)

## 1. 문제 정의

고령 사용자는 모바일 송금 과정에서 두 가지 위험에 자주 노출된다.

- **오송금**: 받는 사람·금액을 잘못 확인하고 그대로 진행해버리는 실수
- **보이스피싱형 송금**: 처음 보내는 상대, 평소보다 큰 금액 등 "잠깐 멈춰야 할" 상황에서도 별다른 제지 없이 송금이 완료되는 UX

기존 은행 앱은 실제 자금이 오가기 때문에, 사용자가 절차 자체를 연습해볼 안전한 공간이 없다. 실수하면 곧바로 실제 피해로 이어지는 구조라, 처음 쓰는 사람일수록 학습 기회 자체가 없다.

> 이 문제 정의는 보도·통계로 정량 검증한 것이 아니라, 고령자 대상 보이스피싱·오송금 이슈가 반복적으로 언급된다는 관찰과 일반적인 문제의식에서 출발한 가설이다. 실사용자 인터뷰나 설문은 진행하지 않았다.

## 2. 타겟 사용자

- **주 사용자**: 모바일 송금 경험이 적거나 불안해하는 고령자
- **보조 사용자**: 가족·도우미(요양보호사, 은행 직원 등) — 고령자를 대신해 접근성 설정(큰 글씨, 음성 안내)을 미리 해주고 서비스를 사용할 준비를 시켜주는 역할 (`/setup` 화면)

## 3. 핵심 가설 (미검증)

1. 실제 돈이 움직이지 않는 "연습 모드"를 제공하면, 사용자가 실수에 대한 두려움 없이 송금 절차 자체를 학습할 수 있다.
2. 한 화면에 한 가지 정보·선택지만 노출하면(단계별 진행, 동시 노출 최소화) 고령 사용자의 이해도와 완료율이 올라간다.
3. "처음 보내는 사람", "평소보다 큰 금액" 같은 상황을 명시적인 확인 단계로 노출하면, 사용자가 진행 여부를 스스로 재검토하게 만들 수 있다.

세 가설 모두 아직 실사용자 테스트로 검증되지 않았다. 현재 설계는 개발자 관찰과 일반적인 접근성 원칙(단계별 노출, 명시적 재확인)에 근거한 추정이다. 사용자 테스트는 v2 계획(문서 하단)에 포함되어야 한다.

## 4. MVP 범위

**포함**

- 첫 방문자를 위한 단계별 처음 화면 투어 (기능을 하나씩 순서대로 소개)
- 연습 송금 / 가상 실제 송금 전체 흐름: 받는 분 선택 → 금액 입력 → 상황별 안전 확인 → 최종 확인 → 완료
- 받는 분 선택: 즐겨찾기·최근 내역에서 고르거나, 은행·계좌번호·이름을 단계별로 직접 입력
- 최근 내역, 자주 보내는 분 목록
- 접근성 설정(큰 글씨, 음성 안내)과 가족·도우미용 사용 준비 화면
- 완료 화면에서의 오송금 대응 안내

**의도적으로 제외한 것 (스코프 아웃)**

- 실제 계좌 연동 및 실자금 이동
- 로그인·회원가입·다중 사용자 계정 (현재는 단일 mock 계좌 하나)
- 거래 실패·대기·취소 등 비정상 상태 (현재 거래는 항상 `completed`로만 기록됨)
- 서버·데이터베이스 (전부 클라이언트 메모리 mock 데이터이며, 새로고침하면 초기화됨)
- 자동화 테스트(단위·e2e) — 현재는 수동 확인과 스크린샷 감사 스크립트(`scripts/audit-ui.mjs`)만 존재

## 5. 핵심 사용자 흐름

```
처음 화면(단계별 투어)
  → 송금 시작
  → 모드 선택 [연습 | 실제]
  → 받는 분 선택 (즐겨찾기 / 최근 / 직접 입력)
  → 받는 분 확인창 ("맞나요?")
  → 금액 입력
  → (조건부) 상황별 안전 확인: 처음 보내는 분 / 50만 원 이상
  → 최종 확인 (받는 분 직접 체크 + 보내기 직전 재확인)
  → 완료 (영수증 + 오송금 대응 버튼)
```

## 8. 위험 신호(안전 확인) 규칙 — 현재 v1

`src/services/transfer-service.ts`의 `calculateRisks`:

- `first-recipient`: 즐겨찾기도 최근 대상도 아닌 받는 분에게 처음 송금하는 경우
- `large-amount`: 금액이 50만 원 이상인 경우

**한계**: 두 규칙 모두 하드코딩되어 있고 임계값(50만 원)도 상수화되지 않은 매직 넘버다. 실제 이상거래탐지(FDS)처럼 여러 조건을 조합하거나 시간대·반복 시도 등을 고려하는 구조는 아니다. 지금은 "상황별 확인이 필요하다"는 컨셉을 보여주는 최소 구현이며, 규칙 엔진화는 v2 대상이다.

## 9. 서비스 계층 / 실제 API 전환 계획

`src/services/transfer-service.ts`가 화면이 데이터에 접근하는 유일한 경로다. 모든 함수가 `Promise`를 반환하도록 만들어져 있어서, 지금은 mock 배열을 즉시 반환하지만 나중에 실제 `fetch` 호출로 바꿔도 화면 컴포넌트 코드는 변경할 필요가 없도록 설계했다.

실제 API로 전환할 때 추가로 필요한 것:

- 로그인·세션 관리 (현재는 사용자 개념 자체가 없음)
- 실패·대기·취소를 포함한 거래 상태 모델과 재시도/롤백 처리
- 감사 로그의 서버 영속화·조회 화면 (현재는 클라이언트 메모리 배열(`transfer-audit-log.ts`)에만 쌓이고, 실패 기록도 없음 — `result`가 항상 `"success"`)
- 잔액 검증, 이체 한도 등 실제 계좌 제약 조건

## 10. 알려진 한계 (v1 기준, v2에서 다룰 것)

- 성능: Lighthouse를 서버 콜드 스타트 직후 측정하면 51점까지 낮게 나올 수 있음. 서버가 예열된 정상 상태에서는 72~86점(측정 방법은 `DEVELOPMENT_LOG.md` 2026-09-07 "Lighthouse 성능 측정 방법 검증" 참고). 뚜렷한 코드 결함보다는 React/Next 런타임 자체의 하이드레이션 비용이 남은 병목
- 위험 신호 규칙이 2개뿐이고 확장 가능한 구조가 아님
- 거래 상태가 `completed` 하나뿐, 실패 시나리오 없음. 감사 로그도 같은 이유로 `"success"` 결과만 존재
- 자동화 테스트: `src/lib`, `src/services`의 순수 함수 단위 테스트는 있고 GitHub Actions로 push·PR마다 자동 실행됨(`.github/workflows/ci.yml`). 화면 컴포넌트·전체 흐름에 대한 테스트(단위/e2e)는 아직 없음
- 접근성: Lighthouse 기준 12개 화면 모두 100점이고, 온보딩 투어의 dialog ARIA·포커스 트랩·Esc 닫기, 하단 내비게이션의 `aria-current` 오류를 수동으로 확인·수정함(자세한 내용은 `DEVELOPMENT_LOG.md` 2026-09-07 "접근성(KWCAG) 점검과 수정" 참고). 다만 이는 자동 도구 + 일부 컴포넌트에 대한 수동 점검이며, KWCAG 2.2 AA 전 항목 공식 인증은 아님. 폼 에러 메시지의 스크린 리더 안내, 색상 외 정보 전달 여부 등은 항목별로 점검하지 않았음
- 사용자/보호자 사이의 알림·모니터링 기능 없음
- 실사용자 테스트로 검증된 가설이 하나도 없음

## 11. 배포 전략 — 왜 지금은 웹/PWA로 유지하는가

**결론**: 당장 네이티브 앱으로 전환하지 않는다. 이 프로젝트는 웹(Next.js) 기반 프로토타입으로 유지하고, 접근성·성능 등도 웹 표준(KWCAG, Lighthouse) 기준으로 계속 검증한다.

**실제 은행권이라면 다르다.** 실자금이 움직이는 송금 기능은 대부분 네이티브 앱(iOS Swift, Android Kotlin, 또는 강하게 하드닝한 Flutter/React Native)으로 나간다. 이유는 UX가 아니라 금융감독원·금융보안원의 보안성 심의 요건 때문이다 — 앱 변조 방지, 루팅·탈옥 탐지, 키보드 보안(가상 키패드, 메모리 덤프 방지), SSL 피닝, 생체인증 연동처럼 OS 레벨 API에 직접 접근해야 하는 항목이 많고, PWA·웹뷰는 브라우저 샌드박스 안에 있어서 이 요건을 온전히 충족하기 어렵다.

**그런데도 지금 이 프로젝트를 네이티브로 바꾸지 않는 이유**: 이 프로젝트는 실자금이 전혀 움직이지 않는 mock 포트폴리오다. 네이티브 재작성은 지금 배운 스택(Next.js/React/TypeScript)을 버리고 완전히 다른 기술(Swift/Kotlin)을 처음부터 익혀야 하는 과잉 확장이며, 이 프로젝트의 목적(송금 흐름·안전장치 설계와 클린 코드 역량을 보여주는 것)에 비해 비용이 훨씬 크다.

**만약 실제 프로덕션으로 간다면 필요한 것** (v2 이후, 별도 트랙):
- 네이티브 앱 전환 및 금융보안원 보안성 심의 대응(변조 방지, 루팅 탐지, 키보드 보안, SSL 피닝 등)
- 접근성 기준도 KWCAG(웹 콘텐츠용)가 아니라 "모바일앱 접근성 지침"(과학기술정보통신부·한국지능정보사회진흥원)으로 다시 점검 — 다만 오늘 발견한 문제 유형(다이얼로그에 역할·라벨 없음, 포커스 관리 안 됨, 대비 부족)은 플랫폼이 바뀌어도 체크리스트 항목으로 그대로 옮겨갈 수 있다.

이 결정은 "웹 접근성 검증이 이 프로젝트에 의미 없다"는 뜻이 아니라, **지금 단계(웹/PWA 프로토타입)에서는 KWCAG·Lighthouse 검증이 정확한 선택이고, 네이티브 전환은 실제 프로덕션이 결정된 뒤에 별도로 판단할 문제**라는 뜻이다.

> 배포 방식은 처음부터 계획한 게 아니었다. 개발 중간에 "실제 은행권 송금 기능은 보안성 심의 때문에 대부분 네이티브(Swift/Kotlin)로 나간다"는 사실을 알게 됐고, 그 시점에는 이미 Next.js 기반으로 화면 흐름과 mock 서비스 계층이 상당히 진행된 상태였다. 지금 네이티브로 새로 시작하는 것과, 웹 프로토타입으로 마무리하고 배포 방식은 별도 판단 과제로 남기는 것 중 후자를 선택했다 — 이 프로젝트의 목적이 "실제 배포 가능한 은행 앱"이 아니라 "송금 흐름·안전장치 설계 역량을 보여주는 포트폴리오"이기 때문이다.
